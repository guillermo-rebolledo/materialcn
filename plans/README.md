# React audit plans

Ten self-contained implementation plans generated by `improve-react` from a
React Doctor scan (v0.9.12) plus a senior audit, at commit **`8872ab1`**.

Baseline: **score 61/100 — 106 warnings, 0 errors, 49 files.**
Of those 106, **84 are not actionable** on deliberate repo conventions; plan
001 silences 78 of them as configuration and the remaining 6 are rejected in
place (see "What was deliberately not planned"). The real findings are 22
warnings across 7 plans, plus 3 additive improvements.

**Post-001 baseline (`doctor.config.mjs`): score 62/100 — 28 warnings, 0
errors, 18 files.** 78 false positives were silenced as configuration
(`only-export-components` 39, `unused-file` 22, `no-barrel-import` 17); every
other rule's count is byte-for-byte unchanged. Note the score barely moved (61
→ 62) — the scoring model is not a straight warning count, so **the per-rule
counts, not the score, are the regression signal** for plans 002–010. The 28
remaining break down as 22 planned findings, 3 on `carousel.tsx:165`, 2
`require-pnpm-hardening`, and 1 `no-array-index-as-key` in story code — the
last three groups being the items under "What was deliberately not planned".

Each plan is written for an executor with **zero context from the originating
conversation**: exact file paths, verbatim current code, exact target code, and
the canonical React Doctor fix recipe inlined. `TICKETS.md` is the same work in
short ticket form, for pasting into a tracker.

## Recommended execution order

**Do 001 first — and it is done.** It does not gate anything technically, but
every other plan's acceptance criterion is "the diagnostic clears and the count
does not regress", and that measurement is meaningless while 78 false positives
dominate the report. Read the acceptance criterion against the **per-rule
counts** in the post-001 baseline above, not against the score: silencing 78
warnings moved the score by a single point, so the score is too coarse to
register any one plan's work.

After 001, nine of the ten plans are independent and can run in any order or in
parallel. The only genuine dependency is **010 → 002**: both edit
`navigation-rail.tsx`'s context value, and doing 010 first would mean editing
the same lines twice.

By value:

1. **001** — makes verification real. Config only, no source changes.
2. **002** and **003** — the two HIGH findings. Both are mechanical, both have
   in-repo exemplars, and together they are the entire performance story.
3. **004** and **005** — small, free, self-contained correctness fixes.
4. **008** — highest-value remaining, but needs real screen-reader testing and a
   design decision; do not schedule it as a quick win.
5. **009**, **007** — additive and hygiene.
6. **006** — smallest payoff, and it costs a permanent divergence from upstream
   shadcn. Declining it is reasonable.
7. **010** — after 002.

## Two things every executor must respect

**The canonical fix is inlined; do not improvise.** Each rule-backed plan quotes
the reviewer-tested recipe from
`https://www.react.doctor/prompts/rules/react-doctor/<rule>.md` verbatim in its
Target section. Where the recipe's generic suggestion is wrong for this codebase
the plan says so explicitly — most importantly in **008**, where the scanner
suggests `<menu>` for `<div role="list">` and `<ul>` is correct.

**Every rule here is classed "Evidence-required risk."** Required evidence is
source code, runtime behavior, *and* measurement. A passing lint run is not
sufficient grounds to keep a change. The performance plans (002, 003) carry a
mandatory React DevTools Profiler before/after, and 008 carries mandatory
VoiceOver and NVDA transcripts. If the measurement shows no improvement, the
correct outcome is to record **Needs evidence** and revert that occurrence — not
to keep a change that buys nothing.

## What was deliberately not planned

- **`only-export-components` ×39** — CLAUDE.md documents the
  `*-variants.ts` / `*-context.ts` split with a precise Fast Refresh rationale.
  Settled decision; handled as configuration in 001.
- **`unused-file` ×22, `no-barrel-import` ×17** — false positives on the
  `*.types.tsx` type-test convention and on `tools/*.mjs` CLI entry points.
  Handled as configuration in 001.
- **`no-pass-data-to-parent`, `no-pass-live-state-to-parent`,
  `no-prop-callback-in-effect`** — all three fire on the same line,
  `carousel.tsx:165`'s `setApi` effect. `api` is set once by Embla rather than
  being live state, so the cost is one extra render per mount, and the pattern
  is the upstream shadcn contract. Over-reported; rejected.
- **`no-array-index-as-key` at `list.stories.tsx:52`** — story code, not shipped.
- **`require-pnpm-hardening` ×2** on `pnpm-workspace.yaml` — a real supply-chain
  hygiene item, but outside the React audit's scope. Worth handling separately.

## If the React Compiler is ever adopted

`jsx-no-constructed-context-values` (002) and `prefer-module-scope-pure-function`
(007) are both **disabled when the React Compiler is enabled**. The project
currently reports `hasReactCompiler: false`. Adopting the Compiler would make
002's memos redundant and retire 007's rule class entirely — worth weighing
before investing in either if a Compiler migration is on the roadmap.
